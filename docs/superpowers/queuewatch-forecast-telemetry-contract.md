# QueueWatch Forecast Telemetry Contract

Date: 2026-09-24

Backend:
- Supabase project: `whvdyxjopfwgzgqqvzaj`
- Edge Function: `submit-queuewatch-forecast`
- Algorithm version accepted by V1 backend: `v1`

## Privacy invariant

The client MUST NOT send the vehicle registration number.

No request field exists for:
- regnum
- registration_number
- plate
- device account identity
- Android ID
- MAC address

The server validator uses an exact allow-list of request keys. Unexpected fields are rejected.

## Common identity fields

Every event contains:

```json
{
  "event_id": "uuid",
  "event_type": "prediction | actual_call",
  "install_id": "random UUID generated by this installation",
  "forecast_session_id": "random UUID for one tracked forecast session",
  "algorithm_version": "v1",
  "checkpoint_id": "official checkpoint UUID",
  "vehicle_type": "CAR | TRUCK | BUS | MOTORCYCLE",
  "started_at": "ISO-8601 UTC timestamp"
}
```

`install_id` is random and is not derived from the phone, user account, vehicle number, or any hardware identifier.

## Prediction event

Exact additional fields:

```json
{
  "observed_at": "ISO-8601 UTC timestamp",
  "current_position": 120,
  "queue_count_same_type": 260,
  "historical_speed": 18.4,
  "live_speed": 24.0,
  "effective_speed": 20.8,
  "predicted_minutes": 343.0,
  "predicted_low_minutes": 285.0,
  "predicted_high_minutes": 405.0,
  "confidence": "LOW | MEDIUM | HIGH",
  "live_sample_count": 4,
  "historical_sample_count": 72,
  "data_gap": false,
  "stale_live_data": false
}
```

`historical_speed` and `live_speed` may be null. All other prediction fields are required.

## Actual-call event

Exact additional fields:

```json
{
  "called_at": "ISO-8601 UTC timestamp",
  "last_in_queue_at": "ISO-8601 UTC timestamp"
}
```

The server requires:
- `last_in_queue_at >= started_at`
- `called_at >= last_in_queue_at`
- no stored prediction for the session may be later than `called_at`.

## Server-side idempotency and limits

The PostgreSQL RPC `ingest_queuewatch_forecast` provides:

- prediction idempotency by unique `event_id`;
- session identity conflict protection;
- one completed call state per forecast session;
- maximum 240 accepted prediction events per installation per hour;
- maximum 30 newly-created forecast sessions per installation per hour.

Retries with the same prediction `event_id` are successful duplicates, not new records.

## Database access

Tables:
- `public.queuewatch_forecast_sessions`
- `public.queuewatch_forecast_predictions`
- view `public.queuewatch_forecast_accuracy`

RLS is enabled on the tables. Mobile `anon` and `authenticated` roles have no direct table privileges or RLS policies.

All writes go through the Edge Function, which performs strict request validation and calls the database RPC using the server-side service role.

## Accuracy fields

The private `queuewatch_forecast_accuracy` view derives:

- actual_minutes;
- signed_error_minutes = predicted_minutes - actual_minutes;
- absolute_error_minutes;
- in_interval.

These are used for aggregate model evaluation and later versioned correction.
